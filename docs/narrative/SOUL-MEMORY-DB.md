# P1-021 혼 기억 DB 스키마 (1차)

> 담당 opus-narrative-lead · 2026-10-24 · 데이터 원본: `docs/narrative/soul_memories.json`
> 스키마(schema — 데이터를 어떤 칸으로 나눠 저장할지 정한 틀). 세계 규칙은 `WORLD-BIBLE.md`, 단서 흐름은 `MYSTERY-3ACT.md`.

## 1. 왜 이렇게 나눴나 — 3가지 원칙

1. **짧게.** 기억 한 줄은 천도 1.5초(연속 0.8초) 동안 시야 가장자리에 떠오른다. 한 문장~두 문장, 40자 안팎. 길면 전투 중에 못 읽고, 못 읽으면 스킵한다. 전문은 도감에서 다시 본다.
2. **이름 있는 혼과 없는 혼을 나눈다.** 미스터리 단서는 **손으로 배치한 "이름혼"**(18명 + 보스 2)만 들고 있다. ProcGen(절차적 생성 — 규칙으로 자동 배치)으로 뿌리는 혼은 `generic_pool`의 짧은 한 줄만 준다. 그래야 무작위 맵에서도 이야기가 깨지지 않는다.
3. **파혼한 이름혼의 기억은 영영 사라진다**(세이브 단위). 그 대신 단서(fact)마다 출처를 2곳 이상 둬서 "한 번 실수로 이야기가 막히지는" 않게 했다. 단, **결정적 단서(decisive)는 출처가 하나뿐**이고 보스를 천도해야만 나온다.

## 2. 칸(필드) 정의

| 칸 | 뜻 | 값 | 플레이에 어떻게 쓰이나 |
|---|---|---|---|
| `id` | 혼 고유 번호 | `S-001`~, 보스 `B-01`~ | |
| `name` | 명부에 적힌 이름 | 문자열 | 파혼 순간 0.3초 흩어지며 보이는 이름(WORLD-BIBLE §5-3) |
| `type` | 떠돈 기간 | `fresh` 갓 죽은 / `year` 해 넘긴 / `old` 오래된 / `boss` | 처결 대기 10/7/4초(W-001~003). 생김새(P1-033)와 1:1 |
| `zone` | 등장 구역 | `config.gd` MAP_ZONE_NAMES와 같은 코드 이름 | Village/Field/Ravine/Shrine/Hub |
| `spawn` | 나오는 방식 | `fixed` 고정 배치 / `event` 특수 / `boss` | fixed는 ProcGen이 구역 안 아무 곳에 한 번 놓는다(위치만 무작위) |
| `seal` | 명부의 인 상태 | `clear` 또렷 / `faded` 흐림 / `missing` 없음 | 🔴제안: faded +0.25초, missing +0.5초 천도 캐스팅. 명부를 고칠수록 줄어든다 |
| `life` | 생전 사연 | 1~3문장 | 도감 전문에만 나온다 |
| `memory_id` | 기억 조각 번호 | `M-001`~ | 도감에 쌓이는 단위. 천도 1회 = 1조각(T-007) |
| `memory` | 천도 중 떠오르는 한 줄 | 40자 안팎 | **설명하지 말고 보여 준다** |
| `tint` | 기억 색 | 말로 적은 색 | 천도 중 시야 가장자리 물드는 색(T-004, MEMORY_TINT). 아트 팔레트 확정 후 코드값으로 |
| `fact` | 미스터리 단서 번호 | `F1`~`F9` 또는 `null` | 같은 fact를 하나라도 얻으면 도감의 "추리판" 칸이 켜진다 |
| `weight` | 단서 무게 | `side` 곁가지 / `main` 본줄기 / `boss` 보스 관련 / `decisive` 결정적 | decisive는 출처 1곳, 천도로만 |
| `funeral` | 장례 목격 대상인가 | true/false | true인 혼을 밤에 천도하면 다음 낮에 장례 장면(P1-024)이 열린다. **fresh만 true** |
| `boss` | 연결 보스 | `B-01` 등 | 보스 낮 단서와 겹치는 기억 |

**지금 데이터(2차):** 이름혼 48(지역별 18·18·12) + 보스 5 = 기억 53 / 단서 15개(F1~F15) / 무명 혼 한 줄 9개. 단서별 출처 표의 최신본은 `SCENARIO-MASTER.md` §4(아래 §3은 1지역만 다룬 1차 기록).

## 3. 단서(fact)별 출처 수 — "아무 순서로 모아도 성립"하는지 확인

| 단서 | 내용(요약) | 혼 출처 | 그 밖의 출처 | 결정적? |
|---|---|---|---|---|
| F1 | 명부 이름이 번진다 | S-001, S-008 | 먹지기 쪽지(1막 시작) | |
| F2 | 큰물 밤, 장례 못 치른 죽음 | S-002 | 낮 소문(나루 영감 단서 D-1), S-006 사연 | |
| F3 | 나루·나룻불이 끊겼다 | S-006, S-011 | 서낭당에서 보이는 꺼진 나룻불(배경) | |
| F4 | 검은 갓 차사가 혼을 깨뜨렸다 | S-004, S-007, S-016 | **B-01 천도로 전모** | 전모만 B-01 |
| F5 | 먹 = 천도된 혼의 기억 | S-005, S-013 | 먹지기 쪽지(2막) | |
| F6 | 원념이 먹을 번지게 한다 | S-014, S-015 | 덩어리 파혼 때 흩어지는 이름들 | |
| F7 | 차사 = 이름 잃은 혼 | S-012, S-017 | | |
| F8 | 당할미 아들이 돌아오지 않았다 | S-009, S-018 | 낮 서낭당 관찰 | |
| F9 | 그 아들이 나다 | — | **B-02 천도로만** | ✅ |

- 출처가 2곳 이상인 단서: F1~F8 전부. 결정적 단서: F4 전모, F9.
- 순서 무관 검사: 어떤 단서도 다른 단서를 알아야 뜻이 통하게 쓰지 않았다(각 문장이 혼자서도 장면이 된다). 모아 놓으면 그림이 된다.

## 4. 천도·파혼 선택에 주는 영향 (기둥 1 점검)

| 상황 | 천도하면 | 파혼하면 | 고민이 생기는가 |
|---|---|---|---|
| 이름혼(인 또렷)이 적 3마리 속에서 무릎 꿇음 | 기억 + 장례 장면(fresh) | 탈출 + 기억 영영 소실 | ✅ 적이 많을수록 파혼 수치가 이득(P1-040) — 이야기 vs 생존 |
| 오래된 이름혼(4초, 인 없음 +0.5초) | 깊은 단서(F5~F7), 그러나 2.0초 캐스팅에 시야 60% | 안전하지만 단서 출처가 하나 줄어듦 | ✅ 가장 위험한 순간에 가장 귀한 단서 |
| 무명 혼 | 넋 + 짧은 한 줄 | 엽전 + 폭발 | 수치 위주 판단(전술 구간). 의도대로 가벼움 |
| 덩어리 | 불가 | 엉킨 이름 목록이 잠깐 보임 | 선택 없음(VISION) — 대신 F6의 증거 |

**화면 표시 제안:** 이름혼은 무릎 꿇을 때 머리 위에 **명부 인 모양**이 떠오른다(또렷/흐림/없음 3단). 플레이어가 "이 혼을 깨뜨리면 무엇을 잃는지" 알고 고르게 하기 위해서다. 모르고 잃으면 선택이 아니라 사고다.

## 5. 코드 담당에게 (code-system-lead용 메모)

- JSON을 그대로 읽어 `id → 혼 데이터` 사전으로 쓰면 된다. 세이브에는 `collected_memories[]`, `lost_memories[]`(파혼한 이름혼), `facts_lit[]`만 저장.
- `fixed` 혼은 해당 구역 ProcGen이 혼 하나를 이 데이터로 바꿔 끼운다(한 번 천도/파혼되면 다시 안 나옴).
- `seal` 캐스팅 가산은 🔴제안 수치 — qa-balance-lead 시뮬 후 COMBAT-SPEC에 ID를 붙여 확정.
