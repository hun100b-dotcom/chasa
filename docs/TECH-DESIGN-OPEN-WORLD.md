# 기술 검토: 넓은 필드 걷기 — 따라오는 카메라와 구역(Zone) 단위 맵 불러오기 (코드·QA)

> 검토 문서다. 코드는 아직 안 바꾼다. 월드 시계(낮밤이 끊김 없이 흐르는 방식)와는 독립이라 먼저 준비할 수 있다. (2026-10-24)

## 0. 지금 상태 (사실, 코드 확인함)
- **카메라는 이미 플레이어를 따라간다.** `GameMain.UpdateCamera`가 초점(focus)을 플레이어 쪽으로 부드럽게 당긴다. 직교(원근 없음) 카메라, 화면 세로 16m, 각도 30°/45°. 그래서 "따라오는 카메라" 자체는 새로 만들 게 아니라 **다듬을 것**이다.
- **맵은 마을 하나(18×14칸)가 전부**다. `MapData`(아트 배치표를 자동 변환한 상수) 하나를 시작할 때 통째로 세운다(`MapView.Build`). 땅 타일·소품이 **하나하나 게임오브젝트**다.
- **충돌은 전역 목록 하나**(`MapLayout.Blockers`)와 맵 경계 밀어내기(`PushOut`). 적도 `ClampToArena`로 한 구역 안에 갇힌다. 소품 목록은 조명(`Atmosphere`)도 읽는다.
- 즉 "넓은 월드"의 걸림돌은 카메라가 아니라 **맵 데이터가 한 덩어리 상수라는 점**이다.

## 1. 카메라: 넓은 필드에서 필요한 것
| 항목 | 지금 | 넓은 필드에서 | 비용 |
|---|---|---|---|
| 따라가기 | 부드럽게 따라감 | 그대로 쓰되 **진행 방향 앞쪽 보기**(look-ahead: 가는 쪽을 약간 더 보여 줌) | 작음 |
| 데드존 | 없음(항상 가운데) | 가운데 작은 영역 안에서는 카메라가 안 움직임 → 멀미·떨림 감소 | 작음 |
| 경계 | 맵 밖도 보임 | 구역 경계 **바깥 어둠**으로 가리거나 카메라를 경계 안쪽에 고정(clamp) | 작음 |
| 시야 크기 | 고정 16m | 지역마다 **시야 높이 값**(탁 트인 들판 18m, 좁은 골목 13m)을 구역 데이터에 | 작음 |
| 연출 | 천도 캐스팅 줌·킥 | 구역 데이터로 **연출 카메라 덮어쓰기**(보스 등장 시 보스까지 포함하도록 줌아웃) | 중간 |
| 빠른 이동 | 없음 | 도착 구역 로드 후 **페이드 인**(화면 암전은 이때만) | 작음 |
- 숫자(데드존 크기, look-ahead 거리, 지역별 시야)는 `data/balance.json`에 둔다. "감으로 잡는 값은 코드에 흩뿌리지 않는다" 원칙대로.
- 조명 마스크(`Atmosphere`)는 화면 기준이라 월드가 커져도 비용이 같다. 단 등불 목록을 **현재 불러온 구역의 소품**에서 읽도록 바꿔야 한다.

## 2. 구역 단위 맵 불러오기
### 2-1. 왜 구역으로 쪼개나
1. **그리기 비용.** 지금처럼 타일 하나가 게임오브젝트면 맵이 20배 커질 때 수천 개가 된다(화면 밖은 자동으로 안 그려도 관리 비용이 든다). 구역별로 **땅을 메시 한 장**으로 합치면 구역당 몇 번의 그리기 호출로 끝난다.
2. **메모리.** 웹(WebGL)·폰 브라우저는 메모리가 빠듯하다. 먼 구역의 그림·소품은 내려야 한다.
3. **규칙 비용.** 막힌 곳·적·소품을 구역별로 가지면 충돌 검사와 적 갱신이 가까운 구역에만 돈다.
4. **작업 분담.** 아트·기획이 구역 파일 하나씩 만들고 고친다(텍스트 파일 기반이라 AI가 다루기 쉬움).

### 2-2. 설계
- **구역 파일** `data/zones/<이름>.json` (엔진 무관, 기존 `data/maps/solgogae_village_layout.json`과 같은 계열): 칸 수, 땅 글자 줄(`S/G/D/Y/P/T`), 소품 목록, 적 자리·종류·수, **위험도(1~5)**, 시야 높이, 환경음 종류, 이웃 구역 이름과 맞닿는 변.
- `tools/gen_map.py`를 확장해 구역 파일 → `ZoneData`(C# 상수)로 자동 생성. 지금 마을은 **구역 0번**으로 그대로 옮긴다(동작 동일).
- **월드 좌표**는 구역마다 시작점(오프셋)을 가진 하나의 연속 좌표. 구역은 변이 정확히 맞닿는 직사각형(경계 띠 겹침 없음). 한 구역 크기 권장 **64×64칸(약 100m 안팎)**: 화면(16m)에 비해 충분히 크고 로드 단위로 가볍다.
- `ZoneManager`(새 부품): 플레이어가 속한 구역 + 이웃 8개를 "켜짐(active)", 그 바깥은 "꺼짐". 경계에서 **구역 반 칸 앞 미리 불러오기**(히스테리시스: 켜는 거리와 끄는 거리를 달리해 경계에서 켜졌다 꺼졌다 하지 않게).
- **웹은 쓰레드(동시 작업)가 없다** → 로드는 한 프레임에 몰아 하지 않고 **프레임당 예산(예: 타일 800개, 소품 20개)**만큼 나눠 한다. 이웃 구역을 미리 켜 두므로 플레이어는 로딩 화면을 못 본다.
- 충돌: `Blockers`를 구역별로 갖고 `PushOut`은 **주변 구역 목록만** 검사(칸 격자 인덱스). 맵 가장자리 밀어내기는 "이웃이 없는 변"에서만.
- 적: 구역이 켜질 때 자리표대로 소환, 꺼질 때 **살아 있는 적은 정리(저장 안 함)**, 처치한 적은 구역별 재생성 시간표로 다시 나옴. 무릎 꿇은 혼은 대기 시간이 규칙대로 흐르다 사라지므로 구역을 벗어나면 "놓친 혼"으로 처리(규칙 기획 필요: **오너 결정 아님, 기획 확정 대상**).
- 소리·조명: 환경음과 위험도는 **플레이어가 선 구역** 값, 조명 등불은 **켜진 구역들의 소품**에서 모은다.

### 2-3. 땅 그리기 최적화
- 구역이 켜질 때 땅 타일들을 **한 장의 메시(+ 타일 그림은 한 장 아틀라스)** 로 합친다. 아트가 타일을 낱장 PNG로 주면 시작 시 한 번 아틀라스로 묶는다(에디터 작업 없이 코드 가능: `Texture2D.PackTextures`). 
- 소품은 y(화면 세로) 기준 정렬이 필요한 그림이라 합치지 않고 개별로 두되, 먼 구역 소품은 꺼서 수를 제한(화면 근처 구역 9개 × 소품 수십 개 = 수백 개는 무리 없음).
- 직교 카메라라 화면 밖 구역은 자동으로 안 그려진다. 문제는 그리기가 아니라 **게임오브젝트 수와 갱신**이므로 위 방식이 맞다.

## 3. 위험과 확인 방법
| 위험 | 대비 |
|---|---|
| 웹 메모리 초과(특히 폰) | 구역 켜짐 최대 9개, 구역당 그림 예산 문서화, PC에서 **메모리 로그**로 확인 |
| 경계에서 끊김·프레임 하락 | 프레임당 로드 예산, PC 숨김 실행으로 **프레임 시간 로그**(95번째 백분위수 16.7ms 이하) |
| 구역 이음매 틈·소품이 경계에 걸림 | 구역 파일 검사 도구: 소품이 변을 넘으면 실패, 이웃 변 길이 불일치 실패 |
| 천도 대기 중 구역 이동 | 규칙(위 2-2) 기획 확정 후 테스트로 고정 |
| 부동소수점 정밀도 | 구역 합쳐 몇 km까지는 문제 없음(1km 이내 오차 mm 단위). 월드가 5km를 넘기면 그때 원점 재설정 |

## 4. 단계(각 단계가 끝나면 게임은 항상 돌아간다)
1. **Z0 데이터 이전**: `MapData` → 구역 0번 `ZoneData`, `gen_map.py` 확장, 구역 파일 검사 도구. 화면·테스트 결과 동일해야 함(Core 테스트로 고정).
2. **Z1 카메라**: look-ahead·데드존·지역 시야·경계 고정. 값은 balance.json. PC 스크린샷으로 비교.
3. **Z2 ZoneManager**: 구역 2개(마을 + 임시 들판)로 켜기/끄기·히스테리시스·프레임당 예산. 켜진 구역 수와 오브젝트 수를 로그로 남겨 테스트.
4. **Z3 땅 메시 합치기 + 아틀라스**: 오브젝트 수 감소를 숫자로 확인.
5. **Z4 적·재생성·소리·조명 연동**: 위험도 기반 장단/환경음, 등불 모으기.
- Z0·Z1은 낮밤 방식이 어떻게 확정돼도 변하지 않는다 → **월드 시계 기획 확정 전에 착수 가능**.

## 5. 결정 필요(기획)
1. 한 구역 크기와 맞닿는 방식(위 64×64 제안으로 괜찮은가).
2. 구역 이동 중 무릎 꿇은 혼의 처리.
3. 꺼진 구역의 적: 살아 있던 적을 기억할지, 켤 때마다 새로 소환할지(권장: 새로 소환 + 처치 재생성 시간표).
